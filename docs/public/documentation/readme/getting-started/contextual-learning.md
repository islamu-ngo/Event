# Private learning and practice

The private learning hub at `/learning` offers available exercises under your
current membership and tenant guidance policy. It stores learning preferences
and practice separately from real event work. Contextual guidance belongs to the
workspace you enter; it never starts a walkthrough or performs real work without
your explicit action.

## Six Private Exercises

Explore event details, sessions/program, ticket capacity, attendees/team and
publication lifecycle through fictional choices and explicit confirmation.
Their results do not create, publish, sell, invite or change a real event.
The sixth exercise reviews a prewritten AI-style suggestion in the shared chat
interface, without contacting an AI provider.

An existing exercise opens at `/learning/demo/{practiceId}`. Opening its address
does not start new practice or recreate a removed shared source. Reset returns
the exercise to its initial choice; clearing removes your private exercise
without deleting real work. Available actions come from the server, not your
browser's interpretation of a role.

A change is shown as applied only after the server confirms it and the current
private resources are refreshed. If a save is unconfirmed or interrupted, reload
to reconcile its outcome before submitting another action. Switching account,
tenant or managed actor discards pending results from the previous context.
Private practice is not embedded into the initial static page.

Private learning saves also complete when privacy-erasure authority uses a
separate embedded database. No configuration change or data migration is
required for this correction. If an earlier save was unconfirmed, reload its
current state before making another choice; do not automatically repeat the
previous action.

Real work starts separately through your workspace's available creation options;
example data is never copied into it. Targeted component and static-rendering
checks cover these boundaries. Full hosted visual and accessibility assurance
remains a programme release gate.

## Review An Authored AI Example

The AI exercise shows a fixed fictional welcome-session suggestion. Choose
Accept example or Reject example, then confirm the simulation to record only
your private exercise result. The result link returns to private learning, not
an event draft. Reset and clear work as they do for the other exercises.

You can also enter `accept-example` or `reject-example` in the composer.
Other text is temporary: it is not sent to a model, stored as conversation
history or copied into real work. Unsupported text leaves the authored choices
available. There are no uploads, reference searches, model tools or live actor
switches in this exercise. Starting a real conversation is a separate workspace
action and does not import this example.

## Reopen Help And Your Private Learning

Help stays available without opening the account menu, including when optional
guidance is hidden or disabled. It explains browsing, participation, personal
work and organization/group collaboration. Administration links reflect the
settings scopes currently offered by the server; Help does not grant them.

Help text follows its own language, so English fallback punctuation remains
readable when the surrounding page uses a right-to-left language.

In deployments with native preference support, signed-in language and direction
changes save only your preferences in the current tenant. Selecting an inherited
value removes your override so future default changes can apply. These changes
preserve your theme and active profile. If the server cannot confirm a save, the
current language stays visible and the picker reports the failure.
The language picker also updates this browser's culture cookies, so a reload can
retain the selected language. If you choose a language while the page is still
loading, the earlier page load won't switch the interface back.

Your own profile or currently selected authorized organization/group context can
show your private learning panel after sign-in. Other visitors see no private
progress. The panel keeps personal preferences and fictional practice separate
from the actor's public activity and from other members' records. A pending
administrator notice remains a distinct explicit action, even when automatic
guidance is suppressed. Acknowledging it records that notice only, not
competence or permission to publish or take payments.

## Configure Tenant Guidance

Tenant administrators can open **Learning guidance** from tenant administration,
including the combined settings layout. The page is at
`/settings/admin/learning`. It controls availability, automatic invitations,
independent invitation/manual audiences, administrator orientation and the four
guidance families. Disabled guidance can still be re-enabled by an administrator
whose current server response permits editing.

Your current personal notice is shown separately from the policy form. Hiding
optional learning or suppressing invitations does not acknowledge or hide a
pending notice. Read it and use its explicit acknowledgement action when the
server offers that action; editing permission does not grant acknowledgement.

When editing is not offered, the page is read-only. A conflicting or unconfirmed
save leaves the draft available for review; use the explicit discard-and-reload
action before saving again. Changes are not replayed automatically. These
settings do not configure providers, clear real setup blockers, expose members'
private progress or install a tour renderer.

## Learning Does Not Grant Production Authority

Instance operators can use **Manage directories** in Getting started when that
action is available. It opens instance directory administration at
`/admin/instance/tenants`. Directory administration is separate from a tenant's
learning settings and does not expose members' private progress.

An active tenant member can learn without publishing or administration rights.
Organization/group context still requires current membership in the appropriate
tenant placement. Completing a lesson does not configure payments, make a
provider available, publish an event or complete tenant setup.

Each learner's state is private to their resolved internal account and tenant.
Another learner, publisher or administrator does not gain a progress/history
reader merely through their role. Switching tenant or account requires a fresh
private context. Do not embed learning state in public page prerendering,
browser transfer state or shared caches.

## Browse Past And Upcoming Events

An empty event search describes the selected dates and filters, not the
workspace's entire event history. The normal view searches upcoming and ongoing
events. When it has no matches, you can search past events and then return to
upcoming events without losing your search or actor, format and age filters.
Existing curated links remain available.

Loading, failed requests and incomplete result traversal are shown separately
from a completed search with no matches. These actions search real public
events; they do not create examples or open a separate archive.

## Announcement Dismissal And Browser Privacy

Anonymous announcement dismissal stays in the browser and is separated by
tenant. Signing in does not copy that marker into your account; signed-in
preferences use the account's server-backed settings. Old browser markers that
did not identify a tenant are ignored, so an announcement may appear again after
this change. If the current tenant cannot be established, no anonymous preference
is read or saved.

The close action keeps the announcement visible and reports a save failure when
storage or the server does not confirm the dismissal. Reconcile the current
state before trying again. Switching account, tenant or announcement settings
invalidates pending results so an older save cannot hide the replacement
announcement. If a newer check shows the same announcement is still visible,
an older dismissal confirmation won't hide it.

Refreshing announcement settings does not repeat a pending dismissal. A tenant
override can be dismissed independently, even if dismissal of the inherited
announcement was never confirmed. If the inherited announcement returns, use
the reconciliation action to check its saved state before trying to dismiss it
again. A refresh that started before the dismissal settled cannot clear that
uncertainty.

Each announcement has a server-issued material edition. Changing its message or
link publishes a new edition, which can appear again after you dismissed the
previous one. Hiding and showing the same announcement does not clear your
dismissal. The edition also identifies its instance or tenant owner: an
instance announcement and a tenant announcement remain separate even when their
text is identical.

An older page may ask you to refresh before dismissing an announcement after its
source changed, even when the visible text looks unchanged. Refreshing does not
automatically repeat a failed save. Closing this optional bar is not consent,
completion of learning, or acknowledgement of a required notice.

## Managing The Announcement Source

Administrators edit a complete announcement rather than several independent
settings. Save changed message or link content to publish a new edition; use
explicit redisplay when unchanged content should appear again. A visibility-only
change retains the material edition.

If you cancel a save already in progress or the editor cannot confirm it, reload
the announcement source before trying again. The editor does not repeat the save
automatically.

A disabled tenant announcement stays selected and hides the bar instead of
falling back to the instance announcement. Remove the tenant override to inherit
the instance source again. An instance lock can mask a tenant's stored source
without deleting it.

Old integer revisions and their dismissal markers are no longer used or
converted. Republish existing scalar-configured announcements through the
announcement editor. Configuration exports contain semantic announcement changes,
not reusable runtime editions or browser/account dismissal evidence.

## Tenant Guidance Choices

The new policy source lets current tenant administrators choose whether
interactive learning is enabled, whether automatic invitations appear, and who
may receive invitations or open learning manually. These two audiences are
independent: active tenant members or tenant administrators. Named tours may
have family-specific restrictions, but those cannot re-enable globally disabled
learning or automatic invitations. Practice follows the global manual audience
rather than borrowing an unrelated tour family's rules.

Default policy enables optional learning for active members and permits
invitations. Reading absent policy uses code defaults without creating stored
state. Administrative integrations read and conditionally replace the policy at
`/api/tenant/settings/documents/learning-guidance`, following its returned
`edit` link and current concurrency stamp. A stale save must refresh rather than
silently overwrite another administrator's changes.

Instance administrators may prevent tenant edits through the registered
instance-only `learning.guidance.allow_tenant_edits` setting. Its default is
true; a tenant cannot override a false instance choice. This uses existing
settings administration, not a new environment variable or secret.

Disabled learning must leave static Help, private history and self-data
deletion/export available; it does not erase evidence or remove the shared
source. Manual-only learning removes automatic invitations, not permitted
manual access. Someone eligible for an invitation may explicitly Start even if
the manual audience is narrower; Replay requires manual eligibility. Neither
path bypasses current membership or workspace authority.
Targeted backend checks cover these policy gates. Rendered learning surfaces
and complete deployment assurance remain separate programme gates.

## Administrator Orientation Acknowledgement

The backend contract lets a tenant opt into an explicit administrator
orientation acknowledgement. Targeted admission and protected-erasure checks
cover its private evidence; the rendered administrator interface and complete
deployment assurance remain separate. Default learning remains optional.

When required, each current tenant administrator sees their own pending or
satisfied status. Another administrator cannot read or acknowledge it for them.
Hiding learning or suppressing invitations does not hide a pending requirement.
Only an explicit acknowledgement records it; completing a tour does not.
Changing invitation settings does not invalidate acknowledgement of the same
orientation material.

Acknowledgement is a personal statement that the material was reviewed, not a
competence assessment or permission to publish, pay or administer another scope.
It blocks no login, recovery, privacy or production action. It does not recreate
a removed shared practice space. Evidence belongs to the learner's account and
tenant and is removed with that account's protected learning erasure.

## What Practice Represents

The backend-defined version-1 `learning-core` practice pack contains six deterministic exercises:

* Event details: choose in-person or online presentation.
* Sessions/programme: choose one or two authored sessions.
* Ticket capacity: choose a synthetic capacity of 12 or 24.
* Attendees/team: choose an attendee or helper example.
* Publication lifecycle: keep the example draft or preview publication.
* AI example review: accept or reject an authored example.

These choices are simulations. They create no production events, tickets,
orders, attendees, payments, emails, webhooks, conversations or federation
effects. A simulated confirmation is not evidence that a live action succeeded.
The exercises require no live AI provider and accept no arbitrary prompt.

## State, Removal And Privacy

The shared tenant learning source is created only by an explicit authorized
start, not by reading a page or enabling a deployment flag. Intentional removal
leaves a tombstone so it stays removed until explicitly recreated. Tenant-wide
source management is distinct from changing a learner's hide/pin/suppression
preferences.

Tour material is version 2, independent of the version-1 practice pack. The backend
retains at most the current and previous tour material versions per family,
with up to 32 semantic steps per family and 256 retained step-evidence rows per
learner. A single claim coordinates concurrent tabs; it expires after
120 seconds without advancing explicit progress. It is not kept alive by
background polling. Manual replay preserves the earlier outcome.

## Current Plans, Progress And Replay

The private named-family plan at `GET /api/learning/tours/{family}/plan` describes
only guidance applicable to the learner's current workspace and, for event
management, the selected event. Families are `Shell`, `Studio`, `EventManagement`
and `NormalAi`. The response includes the captured context, source/plan stamps,
scope and learner revision, with current HAL links indicating claim eligibility.
An earlier response is not permission to act after switching account, tenant or
context.

Creators can use guidance for their own private drafts without receiving a
separate event collaboration role. Current tenant membership, the event and
creating actor's availability, and tenant guidance policy still apply.
Guidance does not grant event editing or publication permission.

Steps are identified by a stable key and version, not their screen position.
Compatible completed evidence survives a temporarily unavailable step or a
reordered tour. Historical completion or skip remains distinct from coverage of
the steps applicable now; updated guidance may introduce new work without
rewriting that history. Completion requires coverage of every applicable step.
The contextual presentation uses the currently rendered shell, Studio, event
management or normal-AI controls. A due invitation is rechecked with the server;
only **Start guidance** acquires a claim. You can skip or choose a one-hour,
one-day or one-week reminder without opening an overlay. **Help** offers manual
replay when the current source permits it, including after automatic guidance
was hidden.

Navigation, a changed account/context, a lost target or a competing dialog stops
the old presentation. A failed or uncertain save never advances a step by
guessing or automatically replaying the request. Missing event-management
entries remain unavailable rather than being replaced with sample events.
An empty real AI response region can be explained without sending a live
message or inventing an AI response.

Release acceptance still requires the separately recorded actual-host and
accessibility checks; compilation and component tests alone do not certify
those behaviors.

Replay must be a deliberate learner choice. Skip and snooze can dismiss an
unclaimed invitation; snooze offers one hour, one day or one week rather than an
arbitrary deadline. An owned claim can be released after its source is removed
without restoring access to that source. No tour starts again automatically,
and lessons never become a hard gate on production work.

During a deliberate replay, Next can move past a step whose current version
you already covered without saving that coverage again. Reviewing known steps
does not extend the claim's lifetime. New coverage still requires a successful
save; an expired claim requires reopening guidance.

Practice is bounded to 20 self/actor contexts and six recipes per context,
1 KiB per record and 128 KiB per learner. Learners may clear their own practice
in a context they can no longer preview. This is not permission to inspect
another person's state.

Internal-account erasure must remove learning across all tenants inside the
existing protected erasure operation, including covered replay and native
PostgreSQL execution. The tenant's shared pack is not another learner's private
history. Physical tenant removal also removes that tenant's learning roots and
children. Learning relationships introduce no deletion path to production users
or actors; existing tenant-retirement rules still govern production data.

## Operator Rollout Boundary

The backend source defines eight `/api/learning` operations: private context,
named-family tour-plan and practice reads; tour claim/action, preference, authored-practice and shared-source
actions. Even reads require the current authenticated tenant member. Responses
and errors are private/no-store. Use the returned HAL links for actions rather
than inferring permission from a role or an earlier response.

Integrations must use the semantic tour contract: tour version 2, expected plan
and policy-source stamps, captured context and explicit `Replay` on claims.
The existing tour-outcome route now accepts `Action` (`Progress`, `Complete`,
`Skip`, `Interrupt` or `Snooze`), not ordinal `StepIndex` or `Outcome` input.
Only progress supplies a step key/version; only snooze supplies a closed duration.
There is no compatibility adapter for old ordinal inputs.

Clients also send the current scope stamp and expected revisions. Claims, actions
and practice carry one stable intent ID for a bounded retry of the same payload.
A conflict requires refreshing the private context and applicable plan. Learning does not cache a
private response to bypass current authorization, and an uncertain commit must
not be automatically repeated as a new action. Source stamps detect stale input;
they grant no access. Observed AI availability is not a guarantee that a provider
credential remains valid or that a later AI request will succeed.

This backend adds learning-owned schema through the normal generated provider
migrations. It adds no tour package, configuration flag, secret, external
provider account or compatibility route. All four semantic migration cohorts
were regenerated and checked against the current model. The original SQL Server
metadata defect was corrected separately; the semantic cohort no longer carries
that unrelated foreign-key change. These checks are not proof of deployment.
Current development acceptance uses freshly created development stores with no
retained data; upgrading an older retained development store is not an accepted
rollout path and is not evidence for this increment. No shared or production
database has been upgraded or reset. Require the normal deployment migration
procedure and selected-provider acceptance before rollout; never hand-edit
generated migrations or reset a shared database.
For PostgreSQL, run the existing declared-purpose migration composition as well:
it installs Runtime tenant-scoped learning rights and the existing protected
Global purpose's limited learner-root erasure rights. Do not grant broad child
table access or production administrator authority to make a learning request
succeed.

API exposure and generated-client rollout remain gated on real private
authorization, concurrency, erasure and provider verification. The later UI
rollout also requires actual keyboard, focus, screen-reader, RTL and
representative-comprehension evidence. Do not describe backend tests as proof
that the complete onboarding experience is ready.

Current verification is SQLite only. The SQLite learning acceptance passes
22 of 22 checks: 9 provider-contract, 7 semantic-persistence, 4 erasure and both
learning migrations. PostgreSQL, SQL Server, MySQL and MariaDB verification is
deferred to the project's server-provider assurance backlog; this increment
makes no certification for any server provider or deployment. Earlier PostgreSQL
receipts and earlier server-provider schema or permission failures are historical
records kept in that backlog, not current results or current SQLite blockers.

The learning hub, authored practice, permanent Help, tenant guidance settings and
announcement dismissal described above are part of this workstream. Final tour
renderer admission, hosted acceptance, real assistive-technology use, actual
browser zoom and representative-user comprehension remain open release gates;
component tests and browser accessibility snapshots don't close them.
Targeted checks cover original-user source retention, rejection after a
concurrent guidance insertion, and live routine drift detection after a warmed
read. API/client regeneration and compilation also passed. These results do not
certify every authority topology or deployment. Require the complete migration
and privacy gates for the selected provider before rollout.

account and authority boundaries.
