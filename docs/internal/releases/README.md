# Governed Releases

This directory contains human-owned release inputs for the future provider-neutral release engine. The current manual release checklist remains authoritative until the trusted release bundle is activated.

Each governed release line uses `docs/internal/releases/<version>/release.yaml` plus `summary.md`. `release-context.v1.json` and `release-notes.md` are generated by `prepare` and must not be edited by hand.

No versioned release directory is canonical until the Project Steward approves that
version and the release operator has exact full Git object IDs. Do not add placeholder
`docs/internal/releases/<version>` directories for unapproved releases.

## `release.yaml`

`release.yaml` fixes the release identity and operator dispositions before context generation. Unknown keys fail closed.

```yaml
Version: 1.1.0
Line: v1.1
Release-Date: 2026-08-14
Base-Stable-Tag: v1.0.0
Previous-Published-Tag: v1.0.0
Release-Range:
  Base-Ref: v1.0.0
  Base-Oid: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
  Previous-Ref: v1.0.0
  Previous-Oid: bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb
Compatibility:
  - v1
Impact-Dispositions:
  breaking: not-applicable
  security: coordinated
  migration: planned
  configuration: not-applicable
  openapi: documented
  operator: documented
```

Rules:

- `Version` is SemVer without build metadata.
- `Line` is the version-line **label** `v<major>.<minor>` and must match `Version`. It is a
  classification, not a Git ref: no branch name is derived from it, and attestation never
  resolves `refs/heads/*`. Maintenance branches, when a backport actually needs one, are named
  `release/<major>.<minor>`; `refs/heads/v*` is reserved for version tags and rejected.
- `Release-Date` is fixed `yyyy-MM-dd`; canonical output must not use the current clock.
- `Base-Stable-Tag` and `Previous-Published-Tag` are explicit `v<major>.<minor>.<patch>` tags.
- `Release-Range` repeats those exact refs and fixes their full lowercase SHA-1 or SHA-256 object IDs. Short IDs, path-like refs, mismatches, missing fields, and unknown keys fail closed; Task 3.1 will resolve and verify the objects against Git.
- For the first governed release only, defined by no reachable governed stable SemVer
  tag in local Git history, both lower-bound fields may instead be the same verified
  `changelog-baseline-YYYY-MM-DD` ref. The adjacent
  `docs/internal/releases/baselines/<ref>.v1.json` evidence must already record the exact full
  baseline tag object ID and target commit ID. This ref is not SemVer history and is
  ignored by release tag discovery; once a governed stable SemVer tag is reachable,
  later release descriptors must use stable SemVer tags.
- `Compatibility` records the release compatibility references Task 2.3 will use for SemVer and range policy.
- `Impact-Dispositions` must explicitly cover `breaking`, `security`, `migration`, `configuration`, `openapi`, and `operator`.

Simple low-impact `feat`, `fix`, `perf`, `revert`, or release-relevant `docs` commits can remain fragment-free when their Conventional Commit subject is sufficient and no required impact category applies.

## `release-context.v1.json`

The release engine emits deterministic renderer input after `release.yaml`, commit policy, and public fragments validate. The context records the selected SemVer without build metadata, the active `v<major>.<minor>` line, the fixed release date, `Base-Stable-Tag`, `Previous-Published-Tag`, minimum ISLAMU bump, release channel, public changes, and full-object evidence. Display IDs start at 12 hexadecimal characters and extend only when collision-safe; prefix collisions that cannot be made unambiguous fail.

Fragments link to the current Git commit through a terminal `Change-Id: CHG-YYYY-NNNN` commit trailer. A linked fragment enriches that current commit into one context change instead of adding a second synthetic change; missing or duplicate links fail. Prerelease contexts are cumulative from the previous stable tag and never advance `main`. `alpha.N`, `beta.N`, and `rc.N` counters must be contiguous, and stable promotion must keep the same base version as the prior prerelease. Backport entries retain both current commit `oid` and full original `Backport-Of`, but are rendered as backports rather than new capabilities on the older line.

Canonical context excludes authors, emails, forge handles or URLs, raw commit bodies, current-clock values, and ambient-locale formatting. git-cliff bump output is comparison evidence only; any disagreement is a review failure, not release authority.

Generate the context and notes from the release branch with:

```bash
dotnet run --project eng/release/src/ISLAMU.ReleaseEngineering/ISLAMU.ReleaseEngineering.csproj -- \
  prepare docs/internal/releases/<version>
```

`prepare` reads only `release.yaml`, `summary.md`, linked public fragments, local Git history, and the promoted trusted renderer bundle supplied through the release environment variables documented in [RELEASE_RUNBOOK.md](../RELEASE_RUNBOOK.md). It writes `release-context.v1.json` and a fully generated `release-notes.md` with fixed section order:

1. `Maintainer Summary` from `summary.md`.
2. `Release-Visible Details` from release-visible commits and applicable impact fragments; omitted when empty.
3. `Complete Commit Range` with every commit in the selected provider-neutral range.

The command prints exactly:

```text
docs(release): prepare <version>

Changelog: skip
Changelog-Reason: release metadata commit
```

## Public Change Fragments

High-impact or grouped public changes use immutable fragments under [changes/](changes/). Fragments are linked by stable `Change-Id`; corrections append a new fragment with `Supersedes` instead of mutating or deleting the prior one.

## `release-evidence.v1.json`

`verify-tag` emits the final canonical release identity after an authorized SSH-signed
annotated tag exists. Its required identity fields include `schemaVersion`,
`version`, `line`, `tagName`, `tagObjectId`, `targetOid`, `candidateOid`,
`candidateManifestSha256`, release descriptor/summary/context/notes hashes, and
trusted bundle manifest/policy/config/trust/tool hashes. The manifest is canonical
release data and intentionally excludes provider run IDs, URLs, collection time,
emails, raw commit bodies, tokens, and secrets.

The durable CI bundle does not recalculate identity. It requires exactly one retained
`release-evidence.v1.json`, verifies its hashes against the adjacent release files
and trusted-tool artifacts, and stores workflow/provider data only as noncanonical
bundle metadata.

## First-release baseline evidence

`verify-baseline` is the only accepted non-SemVer lower-bound verifier:

```bash
dotnet run --project eng/release/src/ISLAMU.ReleaseEngineering/ISLAMU.ReleaseEngineering.csproj -- \
  verify-baseline changelog-baseline-YYYY-MM-DD <full-target-oid> <full-tag-object-id>
```

The command writes `docs/internal/releases/baselines/changelog-baseline-YYYY-MM-DD.v1.json`
after the promoted bundle verifies an authorized SSH-signed annotated tag. It records
the baseline ref, full target commit ID, full tag object ID, and signer authorization
facts. It does not create, delete, move, or sign tags. The baseline evidence is a lower
bound for the first governed release only; it is not a release descriptor and cannot be
published as a version.
